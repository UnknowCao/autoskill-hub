# 反例黑名单（不要做的事）

来自实测暴露的对抗性案例。命中任一条即返工改写，不交付带缺陷的版本。终检（见 [final-check.md](final-check.md)）时对照本表扫一遍。

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| N1 | 同一篇回复内混用 `“”` 与 `「」` | 实测中出现过两次引号样式同现；终检清单有规则但无集中反例时仍被漏掉 | 终检时对全文做一次引号样式扫描，混用即统一到主导样式 |
| N2 | 用户没选作者就擅自套腔调 | 违反 [voice-adoption.md](voice-adoption.md) 的机会性询问约束，用户会失去对文风的控制权 | 未指名时最多询问一次；被拒绝后本会话不再追问 |
| N3 | 把多位作者的声音混在同一篇里 | 两种句法模板叠加产生第三种不存在的腔调 | 一次只加载一份 voice 档案；换声 = 先丢掉旧档案 |
| N4 | 为去 AI 味越权补充事实 | skill 的底线是保留原意，硬补的例子会被当成作者观点 | 机制可以补占位说明（「此处按行业常识补了机制，发布前请核实」），事实必须来自原文或用户 |
| N5 | 深度改写时整段照搬不动 | 表面完成了「深度改写」，实际只做了词级替换，段落节奏仍是机器节奏 | 深度改写的判据：至少完成句子重排 + 弱句合并 + 主语补足三项中的一项 |
| N6 | 用「建议可以考虑」软化返工指令 | 软化措辞会让返工指令失去约束力，实测被判为编码失败 | 反例命中时直接写「改 X 为 Y」，不带商量语气 |
